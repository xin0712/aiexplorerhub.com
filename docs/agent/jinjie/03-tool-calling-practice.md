# Tool Calling 实战：从函数工具到 MCP Server

:::tip 先看结论
工具是 Agent 的手脚。写工具的第一原则不是「功能全」，而是**边界清晰、失败可见**——
一个不会报错的工具，会让 Agent 带着错误结果一路跑下去。
:::

## 这篇解决什么问题

基础篇《Tool Calling 与 MCP》讲的是**机制**：模型怎么发起工具调用、参数怎么传、结果怎么回。
这一篇讲的是**动手**：写一个函数工具、发布一个 MCP Server，并让 Agent 真的用起来。

## 你会得到什么

- 一个能在 Agent 里跑通的函数工具
- 一个自己写的 MCP Server（可被任何支持 MCP 的客户端接入）
- 一套工具设计规则（怎么避免「工具太多选不对」）

## 本篇结构

### 一、工具的本质：一次结构化的函数调用

- 声明（schema）→ 模型决策 → 参数生成 → 本地执行 → 结果回传
- 为什么 schema 写得好不好，直接决定工具能不能被正确调用

### 二、写第一个工具（函数工具）

- 选一个真实需求（如：查数据库、读文件、调 API）
- 参数设计：必填 / 选填 / 类型约束
- 返回值设计：**为什么不该返回一大坨原始数据**
- 错误怎么表达：抛异常 vs 返回错误对象（两种都会发生什么）

### 三、工具设计的三条规则

1. **一个工具做一件事**——名字取不准，说明职责没划清
2. **输入输出要有明确契约**——别让模型猜参数格式
3. **失败要显式**——静默失败比报错危险得多

> 坑：工具返回「空结果」时，模型容易当成「没有这个数据」，而真相可能是**查询失败了**。

### 四、工具太多怎么办

- 症状：工具一多，模型选错、选漏、参数填错
- 三种应对：分组 / 动态筛选 / 分层（先选类别再选工具）

### 五、MCP 是什么（一句话）

- MCP = 把工具/资源的提供方式**标准化**，让工具可以跨客户端复用
- 自己写一个工具，别人不用改代码就能用

### 六、动手：写一个最小 MCP Server

- 环境准备与依赖
- 声明一个工具
- 传输方式（stdio / 网络）
- 在本机客户端里接上它

### 七、跑起来

- 完整代码
- 调用日志：看模型实际发了什么参数
- 故意让它失败一次，看 Agent 怎么处理

### 八、常见坑

- **参数类型不匹配**：模型给字符串，工具要数字
- **工具描述含糊**：模型不知道什么时候该用它
- **返回内容过大**：一次返回几万 token，直接挤爆上下文
- **权限边界缺失**：工具能删库，但没人拦它
