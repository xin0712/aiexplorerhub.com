# 评测你的 Agent：写几个 eval，看它到底行不行

:::tip 先看结论
「感觉还行」不是评价。评测要回答的是：**换一次 Prompt / 换一个模型，效果是变好还是变坏？**
没有 eval，你的每一次改动都是赌博。
:::

## 这篇解决什么问题

进阶篇前面几篇都在「让它能跑」。这篇解决的是**怎么知道它跑得好不好**。
作为开发者，这里只讲**开发期怎么跑几个用例**；至于完整的评估体系（回归、金标准集），放到高级篇。

## 你会得到什么

- 一个最小评测脚本
- 一份可复用的测试用例集
- 「改了 Prompt 之后效果好了吗」的确定性回答

## 本篇结构

### 一、为什么需要 eval

- 场景：你优化了 Prompt，感觉更好了——真的吗？
- 没有量化，就分不清「变好」和「运气好」
- 回归：这次改好了 A，有没有弄坏 B

### 二、评测什么

| 类型 | 例子 | 怎么判 |
|---|---|---|
| 结果正确性 | 算出的数字对不对 | 断言 |
| 工具调用正确性 | 有没有调对工具、参数对不对 | 检查调用记录 |
| 格式合规性 | 输出是不是要求的 JSON | 解析校验 |
| 过程合理性 | 有没有绕远路、重复调用 | 步数 / 成本 |

### 三、写第一批用例

- 从真实失败里收集（比凭空想的有用得多）
- 一个用例 = 输入 + 期望 + 判定方式
- 覆盖哪些：正常 / 边界 / 已知的坑

### 四、动手：一个最小评测脚本

- 读用例 → 跑 Agent → 断言 → 汇总
- 跑一遍看输出
- 故意改坏一处，看它能不能报出来

### 五、只看通过率不够：还要看什么

- 成本（token 消耗）
- 延迟
- 稳定性（同一个输入跑 5 次，结果一致吗）

> 坑：Agent 有随机性。**单次通过不代表稳定**，关键用例要跑多次。

### 六、常见坑

- **用例太少**：3 个用例全过，就以为没问题
- **只测正常路径**：线上出事的往往是边界
- **用例和实现耦合**：照着实现写用例，实现错了用例也是错的
- **只看结果不看过程**：答案对了，但绕了 20 步、花了 10 倍的钱
