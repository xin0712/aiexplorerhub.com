# 评测你的 Agent：写几个 eval，看它到底行不行

:::tip 先看结论
「感觉还行」不是评价。评测要回答的是：**换一次 Prompt、改一行工具、换一个模型，效果是变好还是变坏？**

没有 eval，你的每一次改动都是赌博。这篇写一个 60 行的评测脚本，然后用它抓出一次真实的回归。
:::

## 这篇解决什么问题

进阶篇前面几篇都在「让它能跑」。这篇解决的是**怎么知道它跑得好不好**。

作为开发者，这里只讲**开发期怎么跑几个用例**；至于完整的评估体系（回归、金标准集、线上监控），放到高级篇。

## 一、为什么需要 eval

场景很具体：你改了一版 Prompt，跑了一遍，觉得「比之前好」。

**真的吗？** 还是你只看了这一个用例、而它恰好对上了？

第五篇那个数据可以回答这个问题。同一句「847 和 1523 哪个 ROI 更高」，模型跑了 5 次：

```text
第 1 次  ✅  长度  929  '**1523 的 ROI 更高。** ## 汇总对比（最近 3 天，2026-10-25 ~ 10-27）'
第 2 次  ✅  长度  543  '**1523 的 ROI 更高。** | 广告主 | 近 3 天消耗 | 收入 | ROI | 转化 |'
第 3 次  ✅  长度  637  '**1523 的 ROI 更高。** | 广告主 | 总消耗 | 总收入 | ROI | 转化数 |'
第 4 次  ✅  长度 1004  '**1523 的 ROI 更高。** ## 汇总对比（最近 3 天）'
第 5 次  ✅  长度  626  '**1523 的 ROI 更高。** 近 3 天汇总对比：'
```

**同一个输入，5 次输出 5 个样子**，长度从 543 字到 1004 字。你「跑一遍觉得变好了」——**你看到的是这五次里的哪一次？**

这就是为什么需要 eval：**它把「这一次」变成「每次都」。**

## 二、评测什么

不是所有东西都值得断言。四类里，前两类是必测的：

| 类型 | 例子 | 怎么判 |
|---|---|---|
| **结果正确性** | 算出的数字对不对 | 断言关键数字出现在答案里 |
| **工具调用正确性** | 有没有调对工具、参数对不对 | 检查调用记录 |
| 格式合规性 | 输出是不是要求的 JSON | 解析校验 |
| 过程合理性 | 有没有绕远路、重复调用 | 步数 / 成本 |

**第二类容易被忽略，但它往往比第一类更早发现问题。** 数字算错可能是模型的锅，但「该调工具却没调」通常是你的提示词或工具描述有问题。

## 三、写第一批用例

**关键原则：从真实失败里收集，不要凭空想。**

凭空想的用例长这样：「问一个正常问题，期望正常回答」——这种用例永远能过，因为它没有判定标准。

**一个有价值的用例 = 输入 + 期望 + 判定方式。** 本文的三条都是前面几篇真出过问题的地方：

| 用例 | 输入 | 期望 | 这条防的是什么 |
|---|---|---|---|
| `normal` | 847 最近三天的消耗合计？**只回答数字** | 答案含 `6200` | 最基本的能不能查对 |
| `boundary` | 999 这个广告主最近三天投放怎么样？ | 明确说查不到，**且不能拿别的数字顶上** | 第三篇那个「空数组伪装成查到了」 |
| `multi` | 847 和 1523 哪个 ROI 更高？ | 答案含 `1523`，且至少调了一次工具 | 该调工具却没调 |

**`boundary` 那条有两个条件，第二个才是重点。** 只说「要提到查不到」不够——模型完全可能一边说「没查到 999」一边把 847 的数字搬过来。所以断言写成：

```python
def check_boundary(ans, calls):
    said_unknown = any(k in ans for k in ("没有", "查不到", "不存在", "无此"))
    no_fake = "0.95" not in ans and "6200" not in ans.replace(",", "")
    return said_unknown and no_fake, "应明确说查不到，且不能拿别的广告主的数字顶上"
```

## 四、动手：一个最小评测脚本

骨架就四步：**读用例 → 跑 Agent → 断言 → 汇总。**

```python
def run_agent(question, impl, max_steps=4):
    msgs = [{"role": "user", "content": question}]
    calls, ptok, ctok = [], 0, 0
    for _ in range(max_steps):
        resp, u = chat(msgs, TOOLS)
        ptok += u.get("prompt_tokens", 0)
        ctok += u.get("completion_tokens", 0)
        msg = resp["choices"][0]["message"]
        msgs.append(msg)
        tcs = msg.get("tool_calls") or []
        if not tcs:
            return msg.get("content") or "", calls, ptok, ctok
        for tc in tcs:
            name = tc["function"]["name"]
            args = json.loads(tc["function"]["arguments"])
            calls.append(name)
            try:
                out = json.dumps(impl[name](**args), ensure_ascii=False)
            except Exception as e:
                out = json.dumps({"error": str(e)}, ensure_ascii=False)
            msgs.append({"role": "tool", "tool_call_id": tc["id"], "content": out})
    return "[步数上限]", calls, ptok, ctok
```

**注意它额外返回了三样东西**：`calls`（调了哪些工具）、`ptok`/`ctok`（花了多少 token）。

- `calls` 给「工具调用正确性」用；
- token 给下一节的成本用。

**这是评测脚本和普通 Agent 代码唯一的区别**：它不能只要答案，它要**所有能用来判断的痕迹**。

用例集和断言：

```python
CASES = [
    {"id": "normal",   "q": "847 最近三天的消耗合计是多少？只回答数字。", "check": check_normal},
    {"id": "boundary", "q": "999 这个广告主最近三天投放怎么样？",        "check": check_boundary},
    {"id": "multi",    "q": "847 和 1523 这两个广告主，哪个 ROI 更高？",  "check": check_multi},
]
```

跑一遍：

```text
用例        结果      token   耗时      判定依据 / 实际答案
────────────────────────────────────────────────────────────────────────
normal    ✅ 通过    1241      6.0s  答案里应含 6200
boundary  ✅ 通过    1174      9.6s  应明确说查不到，且不能拿别的广告主的数字顶上
multi     ✅ 通过    2157     10.7s  应查到两个广告主并指出 1523
────────────────────────────────────────────────────────────────────────
通过率 3/3    总 token 4572    总耗时 26.2s
```

### 现在故意改坏一处，看它报不报

我把工具改坏：**忽略 `days` 参数，永远只返回一天**。

```python
def broken_impl(base):
    def wrong_days(adv_id, days=3):
        """坏在：忽略 days 参数，永远只返回一天。"""
        return base(adv_id, days=1)
    return {"query_ad_report": wrong_days}
```

再跑：

```text
⚠ 已刻意改坏：工具忽略 days 参数，永远只返回一天

normal    ❌ 失败    1285      8.4s  答案里应含 6200
                                  实际答案：2100
                                  （注：接口实际只返回了 1 天数据——2026-10-27，`days` 字段显示为 1。
                                   此 2100 是这一天的消耗合计，并非完整三天；如需三天数据请确认查询范围。）
boundary  ✅ 通过    1123      9.1s
multi     ✅ 通过    1715      9.3s
────────────────────────────────────────────────────────────────────────
通过率 2/3
```

**评测抓住了这次回归。** 但它同时暴露了两件事，都比「抓住了」更值得记住：

**① 只有 1/3 的用例抓到了。** `boundary` 和 `multi` 照样通过——它们本来就没查「三天合计」。**一次回归只会被你覆盖到它的那些用例抓到**，这就是为什么用例集要覆盖不同维度，而不是同一个问题问三遍。

**② 模型其实自己发现了异常。** 看那条失败答案的后半句：「接口实际只返回了 1 天数据……并非完整三天」。它诚实报告了。但评测**仍然判它失败**——因为期望是「答出 6200」。

> **评测判的是结果，不是态度。** 模型解释得再清楚，没给出正确数字就是没完成。这两件事要分开。

**用例不是写完就完了。** 上面这次改坏抓出来的失败，就该变成一条新用例——**「从真实失败里收集」是持续的，不是一次性的。**

## 五、只看通过率不够

通过率是及格线，不是全部。至少还要看三样：

### ① 成本

上面三个用例一共 **4572 token**。单看没感觉，但：

- 这是 **3 个用例**。你有 30 个用例、每次改动都跑一遍，就是 45000 token；
- 如果 `multi` 那条从 2157 涨到 4000（比如改提示词让它多查了几轮），**通过率还是 3/3，但成本翻倍了**。

**通过率不变而成本翻倍，是 Prompt 改动最常见的隐性劣化。** 只看通过率就会发现不了。

### ② 延迟

单个用例 6~11 秒，没问题。但如果某个改动让它跑到 40 秒（比如加了重试、多绕了两步），**通过率也可能还是 3/3**。

### ③ 稳定性：同一个输入跑 5 次

这条最容易漏。跑一遍刚才的评测：

```text
═══ 用例 normal：847 最近三天的消耗合计是多少？只回答数字。 ═══
  第 1 次  ✅  长度    4  '6200'
  第 2 次  ✅  长度    4  '6200'
  第 3 次  ✅  长度    4  '6200'
  第 4 次  ✅  长度    4  '6200'
  第 5 次  ✅  长度    4  '6200'
  → 断言通过 5/5    原文不同的份数 1/5

═══ 用例 multi：847 和 1523 这两个广告主，哪个 ROI 更高？ ═══
  第 1 次  ✅  长度  929  '**1523 的 ROI 更高。** ## 汇总对比（最近 3 天，2026-10-25 ~ 10-27）'
  第 2 次  ✅  长度  543  '**1523 的 ROI 更高。** | 广告主 | 近 3 天消耗 | 收入 | ROI | 转化 |'
  第 3 次  ✅  长度  637  '**1523 的 ROI 更高。** | 广告主 | 总消耗 | 总收入 | ROI | 转化数 |'
  第 4 次  ✅  长度 1004  '**1523 的 ROI 更高。** ## 汇总对比（最近 3 天）'
  第 5 次  ✅  长度  626  '**1523 的 ROI 更高。** 近 3 天汇总对比：'
  → 断言通过 5/5    原文不同的份数 5/5
```

**两条用例的对比就是这一节的全部结论：**

| | 断言通过 | 原文不同的份数 |
|---|---|---|
| `normal`（只回答数字） | 5/5 | **1/5**（完全稳定） |
| `multi`（自由发挥） | 5/5 | **5/5**（每次都不同） |

**两个结论：**

1. **断言稳定 ≠ 输出稳定。** `multi` 五次答案长度从 543 到 1004，措辞完全不同——但「1523 更高」这个事实每次都答对了。**所以评测必须断言关键事实，绝不能比对全文。** 拿全文做期望值，你的用例会 100% 失败。

2. **输入约束越强，输出越稳。** `normal` 说「只回答数字」，它五次一字不差；`multi` 让它自由发挥，它就每次都换个排版。**想让它稳，就加约束。**

> 坑：Agent 有随机性。**单次通过不代表稳定**，关键用例要跑多次——尤其是「不该出现某内容」这类断言（比如 `boundary` 里的「不能编数字」），跑一次通过说明不了什么。

## 六、常见坑

**① 用例太少**

3 个用例全过，就以为没问题。**上面的实测给了反例：改坏工具后 3 个用例只抓到 1 个。** 覆盖不同维度（正常 / 边界 / 工具调用 / 格式），比同一个维度写 10 条有用。

**② 只测正常路径**

线上出事的往往是边界。`boundary` 那条用例（查一个不存在的 ID）就是从第三篇真实踩过的坑来的——**它当时的表现是模型拿空数组编了一段话**。

**③ 用例和实现耦合**

照着实现写用例，实现错了用例也是错的。

判断法：**把用例拿给一个没读过你代码的人，他能不能写出判定？** 能，说明用例描述的是需求；不能，说明它描述的是实现。

**④ 只看结果不看过程**

答案对了，但绕了 20 步、花了 10 倍的钱。**这就是为什么要额外记录 `calls` 和 token**——它们让「过程」也可判。

**⑤ 拿全文做期望值**

见上一节。模型每次的措辞都不一样，**断言要抓事实，不要抓文本**。

**⑥ 改动完不跑回归**

这次改好了 A，有没有弄坏 B？**每次改动都该把全量用例跑一遍**——这也是为什么用例集要小、要快（本文 3 条 26 秒，这个量级才可能每次都跑）。

## 七、下一步

到这里，你手上有了一整套「自己写的」东西：Agent 循环、记忆、工具、Runtime、多 Agent、真实接入、评测。

**全部不用框架，全部你能读、能改、能调试。**

那么下一个问题自然就来了：**既然手写能做，为什么还有那么多人用框架？**

答案不是「框架更好」，而是「**在某些场景下，框架替你做的那部分值那个钱**」——但这个判断你只有**自己搭过一遍**才能做出来。

**下一篇是进阶篇的最后一篇**：《框架深挖·动手篇》——同一个任务，用三个框架各搭一遍，然后比手感、比代码量、比调试体验。
