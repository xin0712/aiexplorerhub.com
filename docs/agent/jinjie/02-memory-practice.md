# Memory 实战：让 Agent 记住事

:::tip 先看结论
模型**本身没有记忆**——它每次只能看到你这次塞进 `messages` 的东西。
所以「记住」不是模型的能力，而是**你代码要不要把历史带上**。

这篇我们用不到 150 行代码实现两件事：**短期记忆**（一轮任务内别断线）和**长期记忆**（跨会话还能用上）。
:::

## 这篇解决什么问题

上一篇《手写一个最小 Agent 循环》跑通的骨架有个明显缺陷：`run_agent()` 一返回，`msgs` 就销毁了——**下次对话从零开始**。

基础篇《Memory 记忆系统深度解析》讲的是**原理**：为什么需要记忆、分几类、架构长什么样。
这一篇讲的是**实现**：真的存进去、真的取回来，并且验证它确实起作用了。

## 一、先分清：三种「记忆」不是一回事

很多人把「记忆」当一个东西，结果该压缩的没压缩、该持久化的丢了。先拆开：

| 类型 | 生命周期 | 存在哪 | 解决什么 |
|---|---|---|---|
| **对话历史** | 一次任务内 | 内存（`msgs` 变量） | 当前任务别断线 |
| **会话记忆** | 一次会话内 | 内存 + 窗口 | 连续对话能接得上 |
| **长期记忆** | 跨会话 | **外部存储** | 用户偏好、项目约定 |

这篇先解决**第一种和第三种**——它们最容易看出差别。

## 二、长期记忆的两个动作：存 + 取

长期记忆说穿了就两件事：

1. **存**：把值得记的东西写到外部（文件、数据库、向量库）
2. **取**：下次对话开始时，把它捞出来放进上下文

关键在「值得记」的判断——**不能什么都存**，否则噪音会淹没信号。

值得存的：

- 用户偏好（「我们用 pnpm 不用 npm」）
- 项目约定（「这个仓库用 ESM」）
- 反复出现的背景（「我们的部署在阿里云」）

不该存的：

- 一次性的中间结果（「刚才查到天气是 12 度」）
- 模型自己的推理过程
- 任何能从代码/文档里读出来的东西

## 三、动手：最小实现

**先不引向量库**。记忆条目少的时候，一个 JSON 文件就够——先把链路跑通，再谈优化。

### 存储层

```python
import json, os

MEM_FILE = "memory.json"

def load_memory():
    if not os.path.exists(MEM_FILE):
        return []
    try:
        with open(MEM_FILE, encoding="utf-8") as f:
            return json.load(f)
    except Exception:
        return []          # 文件坏了当空的——记忆丢了不该让 Agent 崩

def save_memory(items):
    with open(MEM_FILE, "w", encoding="utf-8") as f:
        json.dump(items, f, ensure_ascii=False, indent=1)
```

### 给 Agent 两个工具

记忆不是自动发生的——**得让 Agent 有「记」和「想」的动作**：

```python
def remember(fact: str) -> dict:
    """记下一条关于用户的长期事实。"""
    items = load_memory()
    items.append({"fact": fact})
    save_memory(items)
    return {"ok": True, "total": len(items)}

def recall(keyword: str = "") -> dict:
    """取回记忆。条目少时全量返回就够。"""
    items = load_memory()
    if keyword:
        items = [m for m in items if keyword in m["fact"]]
    return {"items": [m["fact"] for m in items]}

TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "remember",
            "description": "记下一条关于用户的长期事实（偏好、约定、背景）。当用户主动说明这类信息时调用。",
            "parameters": {
                "type": "object",
                "properties": {"fact": {"type": "string", "description": "要记住的事实，一句话"}},
                "required": ["fact"],
            },
        },
    },
    {
        "type": "function",
        "function": {
            "name": "recall",
            "description": "取回之前记住的关于用户的事实。当需要了解用户偏好或背景时调用。",
            "parameters": {
                "type": "object",
                "properties": {"keyword": {"type": "string", "description": "可选的筛选关键词"}},
            },
        },
    },
]

TOOL_IMPL = {"remember": remember, "recall": recall}
```

> **工具描述写得好不好，直接决定它记得准不准。**
> 上面 `remember` 的描述里写了「当用户主动说明这类信息时调用」——这句是给模型的判断依据。
> 少了它，模型可能把「今天天气不错」也记下来。

### 关键一步：把记忆注入系统提示词

这是最容易漏的一环。光存不取，等于没存：

```python
BASE_PROMPT = "你是一个得力的编程助手，回答简洁、直接。"

def build_system_prompt():
    items = load_memory()
    if not items:
        return BASE_PROMPT
    lines = "\n".join(f"- {m['fact']}" for m in items)
    return f"{BASE_PROMPT}\n\n你知道的关于用户的背景：\n{lines}"
```

然后 `run_agent()` 里把系统提示词换成它：

```python
def run_agent(question: str) -> str:
    msgs = [
        {"role": "system", "content": build_system_prompt()},   # ← 每次任务开始时注入记忆
        {"role": "user", "content": question},
    ]
    # 下面的循环和上一篇一样：模型决策 → 执行工具 → 回传结果
    ...
```

`chat()` 和循环部分与上一篇完全相同，这里不重复。

## 四、跑起来

**第一次对话**——用户说明一个偏好：

```text
你：我们项目用 pnpm，不用 npm。记一下。

  [第1步] remember({'fact': '用户的项目使用 pnpm，不使用 npm。'}) -> {"ok": true, "total": 1}
已记住：项目用 pnpm，不用 npm。
```

注意：**模型自己判断该调 `remember`**，还自己把话说通顺了。你只给了原始信息。

存下来的文件：

```json
[
 {
  "fact": "用户的项目使用 pnpm，不使用 npm。"
 }
]
```

**第二次对话**——新起一个进程（等于新会话），**一个字都没提 pnpm**：

````text
你：帮我看看这个项目该用什么包管理器装依赖？

直接执行：

```bash
pnpm install
```

如果项目里有 `pnpm-lock.yaml`，务必保留它并使用 pnpm install --frozen-lockfile（CI 场景）保证依赖版本一致。
````

它记得。**这就是跨会话记忆。**

## 五、证明它真的在起作用

「感觉它记住了」不够说服力。做个对照实验——同样的问题，清空记忆再问一遍：

| | 有记忆 | 清空记忆后 |
|---|---|---|
| 问题 | 「我要装个新依赖，用哪条命令？」 | 同一个问题 |
| 回答 | **`pnpm add <包名>`** | 「你用的是哪个语言/包管理器？」 |

有记忆的直接给答案，没记忆的**反问你**。差别一目了然。

**建议你也做这个对照**——它是判断「记忆机制有没有真的生效」最直接的办法。

## 六、短期记忆：长对话怎么办

上面解决的是「跨会话」。还有另一半：**一次会话里聊久了，`msgs` 会撑爆上下文窗口。**

三种策略，各有代价：

| 策略 | 做法 | 代价 |
|---|---|---|
| 全量保留 | 什么都不做 | 迟早爆窗口 |
| 滑动窗口 | 只留最近 N 轮 | **早期信息直接丢** |
| 摘要压缩 | 把旧对话压成一段摘要 | 会丢「为什么这么做」的推理链 |

**实用做法是组合**：保留最近几轮原文 + 更早的压成摘要。

一个粗略的触发时机：**当历史 token 接近上下文窗口的 70~80% 时压缩**。
留出余量是因为——你还得给工具返回、系统提示、模型输出留空间。

> 坑：压缩掉的往往是「推理过程」，留下的是「结论」。
> 结果是模型知道「用了 pnpm」，但不知道为什么（因为项目有两套构建流程）——下次遇到边界情况它就判断错了。

## 七、什么时候该升级成向量检索

上面的实现把全部记忆塞进系统提示词。**条目少时没问题，多了就不行**：

| 记忆条数 | 合适做法 |
|---|---|
| 几十条以内 | 全量注入（本篇的做法） |
| 几百条以上 | 得检索——只把相关的捞出来 |

检索有两条路：

- **关键词检索**：简单，但「用户说的 pnpm」和「包管理器偏好」匹配不上
- **向量检索**：语义匹配（能对上），但要额外的 embedding 服务

> ⚠️ 注意：**DeepSeek 没有 embedding 接口**（实测返回 404）。
> 要用向量检索得另接一家（火山方舟、硅基流动、阿里的百炼都有）。这是「升级」时才付的成本。

**向量检索的坑**：检索失败比检索不到更糟——取回**不相关**的记忆会污染上下文，让模型基于错误前提回答。

## 八、常见坑

**① 只存不取**
写了 `remember` 却没在系统提示词里注入。存了一堆，模型一条也看不到。

**② 什么都记**
把「今天天气不错」也存下来。噪音多了，真正有用的偏好就被淹没了。

**③ 记得住但取不回**
条目一多，关键词匹配失效（「pnpm」搜不到写着「包管理器偏好」的那条）。这时候才需要向量检索。

**④ 记忆无限膨胀**
没有清理和过期机制。建议加字段记录「什么时候记的、多久没用了」，定期清。

**⑤ 存了不该存的**
记忆文件是**明文**。用户随口说的密码、密钥、个人信息，不该进去。
如果要存敏感信息，至少做加密——但更好的做法是**一开始就别存**。
