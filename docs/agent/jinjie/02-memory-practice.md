# Memory 实战：让 Agent 记住事

:::tip 先看结论
Memory 分两种：**短期**（这一轮的对话上下文）和**长期**（跨会话的沉淀）。
短期靠「上下文管理」，长期靠「存 + 取」两件事——**存得准、取得回**，才算真的记住了。
:::

## 这篇解决什么问题

基础篇《Memory 记忆系统深度解析》讲的是**原理**：为什么需要记忆、记忆分几类、架构长什么样。
这一篇讲的是**实现**：真的接一个向量库，真的存进去，真的取回来，并且让它在真实任务里起作用。

## 你会得到什么

- 一个能跨会话记住用户偏好的 Agent
- 一套「什么时候存、什么时候取」的判断规则
- 一个上下文压缩的实现（长对话不爆窗口）

## 本篇结构

### 一、先分清：三种「记忆」不是一回事

- **对话历史**：这一轮的上下文，天然存在，会随轮数膨胀
- **会话记忆**：这次会话结束就没了，但下次打开还在
- **长期记忆**：跨会话、跨项目的沉淀

> 坑：把它们混成一个「记忆」概念，会导致该压缩的没压缩、该持久化的丢了。

### 二、短期记忆：上下文怎么管

- 窗口有多大：不同模型的上下文长度差异
- 三种策略与代价：**全量保留** / **滑动窗口** / **摘要压缩**
- 什么时候触发压缩（阈值怎么定）
- 压缩会丢什么（往往丢的是「为什么这么做」的推理链）

### 三、长期记忆：存什么

- 存什么：用户偏好 / 项目事实 / 踩过的坑 / 决策记录
- 不存什么：一次性的中间结果（存了就是噪音）
- 存的形式：纯文本 / 结构化字段 / 向量

### 四、取回来：检索怎么做

- 向量检索的原理与局限
- 关键词检索 vs 向量检索（什么时候用哪个）
- 混合检索
- **检索失败比检索不到更糟**：取回不相关的内容会污染上下文

### 五、动手：接一个向量库

- 选型考虑（本地 / 云、成本、是否要额外依赖）
- 最小实现：写入 + 查询
- 跑一个真实场景：让 Agent 记住「这个项目用 pnpm 不用 npm」

### 六、跑起来

- 完整代码
- 运行输出：第一次说明、第二次自动遵守
- 验证它真的记住了（换个说法再问一次）

### 七、常见坑

- **存了但取不回**：检索阈值设置不当
- **取回无关内容**：把噪音当知识，污染后续推理
- **记忆无限膨胀**：没有清理与过期机制
- **隐私与敏感信息**：记住的东西可能是不能记的
