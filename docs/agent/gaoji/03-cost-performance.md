# 成本与性能：token 是要花钱的

:::tip 先看结论
Agent 的成本不是「一次请求多少钱」，而是**一次任务跑下来调了多少次模型**。
控制成本的主战场在上下文管理，不在选更便宜的模型。
:::

## 这篇解决什么问题

单次对话很便宜，但一个 Agent 任务可能调几十次模型，每次还带着很长的上下文。
这篇讲**怎么把账算清楚、把成本降下来、把速度提上去**。

## 你会得到什么

- 一套成本核算方法（知道钱花在哪）
- 四种降本手段及其代价
- 速度优化的着力点

## 本篇结构

### 一、先把账算清楚

- 成本 = 输入 token + 输出 token（两者单价常常差好几倍）
- **Agent 的成本乘数**：一次任务调 N 次模型，上下文还越滚越大
- 算一个真实例子：单轮对话 vs 10 步 Agent 任务

### 二、钱花在哪

| 大头 | 说明 |
|---|---|
| 上下文重复发送 | 每一轮都把历史重发一遍 |
| 工具返回内容过大 | 一次返回几万 token |
| 无谓的重试 | 不可重试的错误也重试 |
| 用大模型干小事 | 格式转换、分类这类活 |

### 三、降本手段（各有代价）

**① 上下文管理**
- 摘要压缩、滑动窗口、只带必要历史
- 代价：可能丢掉关键信息

**② 大小模型分层**
- 简单任务用小模型（分类、提取、格式转换）
- 复杂推理用大模型
- 代价：路由判断本身要成本，分工不当反而更贵

**③ 缓存**
- Prompt 前缀缓存（同一段系统提示复用）
- 结果缓存（同样输入不重复算）
- 代价：缓存失效策略要设计

**④ 减少轮次**
- 一次多调几个工具（并行工具调用）
- 更明确的 Prompt 减少来回
- 代价：并行可能带来新的错误处理复杂度

### 四、性能：为什么这么慢

- 延迟来源：模型推理时间 + 工具执行时间 + 网络往返
- 串行 vs 并行：能并行的工具别串着跑
- 流式输出：让用户先看到东西
- 小模型做前置判断：先判断要不要调大模型

### 五、成本监控

- 按任务统计（不是按请求）
- 设预算上限，超了就停
- 异常告警（某天成本突然翻倍）

### 六、常见坑

- **只看单价**：便宜模型多跑 5 轮，总价更高
- **无上限**：Agent 卡住时无限烧钱
- **缓存不设失效**：数据更新了还在返回旧结果
- **优化错方向**：花大力气省了 5%，问题其实在上下文重复发送
