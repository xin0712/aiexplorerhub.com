# 安全与权限：别让它删了你的库

:::tip 先看结论
给 Agent 工具权限，本质上是**给一个会犯错的实习生生产环境权限**。
安全设计的核心不是「相信它不会乱来」，而是**即使它乱来，也伤不到要害**。
:::

## 这篇解决什么问题

Agent 能调工具，意味着它能改数据、发消息、花钱。
这篇讲**怎么在放权的同时不失控**——权限、沙箱、审计、审批。

## 你会得到什么

- 一套权限分级的方法
- 高风险操作的人机确认机制
- 一份审计清单

## 本篇结构

### 一、先给危险分级

| 级别 | 例子 | 处理 |
|---|---|---|
| 只读 | 查数据、读文件 | 放行 |
| 写入 | 改配置、写文件 | 记录 + 限额 |
| 对外 | 发消息、调付费 API | 需确认 / 限额 |
| 不可逆 | 删数据、发邮件、转账 | **必须人工确认** |

> 关键：**按可逆性分级**，不是按「看起来危险不危险」。

### 二、最小权限原则

- 工具默认只读
- 写权限单独申请、单独账号
- 生产凭据和开发凭据分开
- 凭据绝不进代码仓库

### 三、沙箱

- 为什么需要：Agent 执行的代码可能出错、可能是恶意的
- 常见隔离手段：容器、虚拟环境、受限目录
- 网络出站限制（防止数据外泄）

### 四、高风险操作的人工确认

- 哪些操作必须确认（不可逆的全都要）
- 确认界面要显示什么（**具体参数**，不是「确认执行吗」）
- 超时怎么办（默认拒绝，不是默认同意）

### 五、审计

- 记什么：谁、什么时候、调了什么工具、什么参数、结果如何
- 为什么：出事后要能还原现场
- 留多久

### 六、提示词注入：一个容易被忽略的洞

- 场景：Agent 读了一段外部内容，内容里写着「忽略之前的指令」
- 为什么危险：外部内容是不可信输入
- 怎么防：把外部内容当数据不当指令、关键操作仍需确认

### 七、常见坑

- **权限给太大**：「先跑起来再说」的写权限，最后忘了收
- **确认界面信息不足**：只问「确认吗」，用户不知道该确认什么
- **认为内网就安全**：内网 Agent 一样能删内网的数据
- **凭据进日志**：排查日志时把密钥打印出来了
