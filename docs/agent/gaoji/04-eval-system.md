# 评估体系：从跑几个 eval 到持续监控

:::tip 先看结论
开发期的 eval 回答「这次改动有没有变好」；
生产期的评估体系回答「**今天线上是不是变差了**」——两者不是一回事。
:::

## 这篇解决什么问题

进阶篇讲了开发期怎么跑几个用例。这篇讲**把这套东西变成体系**：
金标准数据集、回归、灰度、线上监控——让效果可量化、可追溯、可回滚。

## 你会得到什么

- 一套评估体系的分层设计
- 金标准数据集的建法
- 「效果变差了怎么发现」的机制

## 本篇结构

### 一、三个层次

| 层次 | 回答什么 | 频率 |
|---|---|---|
| 开发期 eval | 这次改动有没有变好 | 每次改动 |
| 回归测试 | 有没有弄坏别的 | 发布前 |
| 线上监控 | 真实使用中是否变差 | 持续 |

### 二、金标准数据集

- 从哪来：真实失败案例 > 真实使用日志 > 人工构造
- 多大够用：**宁可少而准**，20 个好用例胜过 200 个凑数的
- 怎么维护：线上出新的失败模式就补进去
- 标注一致性：判定标准要明确（不然不同人判得不一样）

### 三、自动判定 vs 人工判定

- 能自动判的：格式、数值、工具调用是否正确
- 要人工判的：回答质量、语气、是否恰当
- **用模型判模型**：可行但要知道它的偏差，关键用例别全靠它

### 四、回归：改动不能弄坏原有的

- 每次改动跑全量用例
- 关键用例单独标记，挂了直接拦发布
- 记录历史通过率（看趋势，不只看单次）

### 五、灰度与回滚

- 新版本先小流量
- 关键指标对比（不只是「没报错」）
- 出问题能快速回滚

### 六、线上监控

- 监控什么：成功率、成本、延迟、用户反馈
- 隐式信号：用户重问、手动纠正、直接放弃
- 告警阈值怎么定

### 七、常见坑

- **用例集一成不变**：线上出了新问题，用例集里没有
- **只测通过率**：答案对了但成本翻倍，没人发现
- **靠感觉判断效果**：改完觉得好，实际变差了
- **评估集污染**：拿评估集去调 Prompt，等于考试前泄题
