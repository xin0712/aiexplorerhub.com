# 框架选型·源码级：拆开看它们怎么实现的

:::tip 先看结论
框架的差异，读文档看不出来，**读源码才看得出来**——
同样是「多智能体」，有的靠图调度，有的靠角色对话，有的靠工具回环。机制不同，能做的事就不同。
:::

## 这篇解决什么问题

资料篇给了清单（有哪些）、进阶篇做了动手对比（用起来什么感觉）。
这篇是**源码级**：拆开看它们的架构机制，并回答「我这个场景该选谁」。

## 你会得到什么

- 三种范式在源码层面的差异
- 一套选型的判断框架
- 「这个框架能不能改」的判断依据

## 本篇结构

### 一、选型问卷：先问五个问题

1. 流程是**固定**的还是**动态**的
2. 需不需要**断点续跑**（任务跑一半崩了怎么办）
3. 要不要**人工审批节点**
4. 团队技术栈是什么（Python / TS / Java）
5. 会不会被**锁定**（换框架成本多大）

### 二、拆解维度

| 维度 | 看什么 |
|---|---|
| 执行模型 | 图调度 / 角色对话 / 工具回环 |
| 状态管理 | 状态存哪、能不能持久化、能不能恢复 |
| 扩展方式 | 加一个能力要动多少代码 |
| 依赖与体积 | 拉进来多少依赖 |
| 可观测性 | 中间状态能不能看到 |

### 三、图编排类（以 LangGraph 为例）

- 核心抽象：状态 + 节点 + 边
- 状态怎么在节点间流转
- 持久化与断点续跑怎么实现
- **源码看点**：状态更新是覆盖还是合并
- 适合与不适合

### 四、角色多智能体类（以 CrewAI 为例）

- 核心抽象：Agent + Task + Crew
- 角色之间怎么协作
- **源码看点**：结果怎么在角色间传递
- 适合与不适合

### 五、轻量运行时类（以官方 SDK 为例）

- 核心抽象：循环 + 工具 + 交接
- 为什么代码量最小
- **源码看点**：主循环的退出条件
- 适合与不适合

### 六、选型结论怎么下

- 场景 → 优先选
- 什么时候该用框架、什么时候自己写
- 什么时候该换框架（出现什么信号）

### 七、常见坑

- **按热度选**：star 多不等于适合你
- **只看 demo**：demo 都很优雅，生产都很脏
- **忽略维护状态**：选了一个已进维护模式的框架
- **低估迁移成本**：框架深度耦合后，换框架等于重写
- **用框架做框架擅长之外的事**：硬掰会很痛苦
