# 可靠性：怎么让 Agent 不跑飞

:::tip 先看结论
Agent 的不可靠，绝大多数不是模型不行，而是**没人给失败设计出路**。
可靠性 = 出错时你知道、能停、能恢复、能查明原因。
:::

## 这篇解决什么问题

Demo 里的 Agent 一路顺利；换上真实数据、真实网络，它就开始各种离谱。
这篇讲的是**怎么让它跑不飞**，以及飞了之后怎么接住。

## 你会得到什么

- 一份 Agent 可靠性的检查清单
- 四种典型失控模式的应对方案
- 「什么该自动处理、什么该叫醒人」的判断依据

## 本篇结构

### 一、Agent 是怎么跑飞的（四种典型）

| 模式 | 症状 | 后果 |
|---|---|---|
| 死循环 | 反复调同一个工具 | 烧钱、任务永不结束 |
| 越权 | 调了不该调的工具 | 数据被改 / 被删 |
| 幻觉行动 | 基于错误信息继续执行 | 结果全错还理直气壮 |
| 静默失败 | 出错被吞掉 | 以为成功了，其实没有 |

### 二、防死循环

- 步数上限（最有效的一招）
- 重复检测：同一个工具 + 同一组参数连续调用
- 成本上限：token 超预算就停
- 兜底：达到上限后怎么收敛（输出已完成部分 + 说明未完成）

### 三、超时与重试的正确姿势

- 每层都要有超时（模型 / 工具 / 整体任务）
- 什么可重试、什么不可重试
- 指数退避 + 抖动
- **幂等性**：重试前先问「做两次会怎样」

### 四、兜底：出错时给什么

- 好的兜底：明确说明「哪一步失败了、为什么、已完成什么」
- 坏的兜底：返回一个看起来像答案的默认值
- 原则：**失败要说出来**，不要假装成功

### 五、可观测性：出了问题怎么查

- 必须记录：每一步的输入、输出、耗时、token
- 追踪一次完整执行（trace）
- 日志保留多久、包含什么

### 六、人工介入的边界

- 该自动处理：临时网络故障、可重试的限流
- 该叫醒人：凭据失效、不可逆操作、成本异常、连续失败

### 七、常见坑

- **只有重试没有上限**：故障时放大压力
- **catch 了什么都不做**：问题被藏起来
- **没有日志**：出事只能猜
- **兜底返回假成功**：最危险的一种——问题被伪装成正常
