这个页面用于持续沉淀 Agent 相关术语。

| 序号 | 名词 | 解释 | 例子 |
| --- | --- | --- | --- |
| 1 | Runtime | Agent 的运行时执行层，负责调度模型调用、工具调用、状态管理、超时重试与任务恢复，保证任务在真实系统中可控执行。 | 当用户发起“生成周报并发送邮件”时，Runtime 会按步骤调用检索、总结、邮件发送等能力，并记录每一步状态。 |
| 2 | AI Native | 指从产品设计到技术架构都以 AI 为中心构建的系统形态，而不是在传统系统上简单叠加 AI 功能。 | 一个 AI Native 的知识库产品，会默认用语义检索、Agent 协作和自动总结驱动核心流程，而不是仅加一个聊天入口。 |
| 3 | VPC隔离 | 通过虚拟私有云（VPC）将企业网络环境与公网隔离，限制 Agent、模型服务和数据资源的访问边界，以提升安全性与合规性。 | 企业把 Agent Runtime 部署在专属 VPC 中，只允许访问白名单数据库和内部 API，外部网络无法直接访问核心数据。 |
| 4 | 审计日志 | 对 Agent 的关键操作进行可追踪记录的日志机制，通常包含操作者、时间、动作、目标资源与结果，用于安全审计与问题追溯。 | 当某个 Agent 读取了敏感文档并调用外部工具时，系统会在审计日志中记录“谁在何时对哪些数据做了什么操作”。 |
| 5 | PR | Pull Request 的缩写，指在 Git 平台上提交的一组待合并代码变更，用于代码评审、讨论和协作合并。 | 开发者完成功能后创建一个 PR，团队成员在 PR 里 review 代码、提出修改意见，确认后再合并到主分支。 |
| 6 | Prototype | 原型版本，指用于快速验证需求、交互或技术可行性的早期产品形态，强调“先验证再完善”。 | 团队先用一周做出 AI 助手 Prototype，验证用户是否真的需要“自动整理日报”功能，再决定是否正式开发。 |
| 7 | CIO | Chief Information Officer 的缩写，通常指企业中的首席信息官，负责信息化战略、技术治理与数字化能力建设。 | 在企业推进 Agent 平台时，CIO 需要统筹数据安全、系统集成、预算投入和技术路线。 |
| 8 | Tool Calling（Function Calling） | 指模型在任务执行过程中按结构化参数调用外部工具（如 API、数据库、搜索、脚本）的能力，是 Agent 从“会回答”走向“会执行”的关键机制。 | 用户让 Agent 分析昨日投放数据时，Agent 通过 Tool Calling 自动调用 SQL 工具查询数据，再生成结论和建议。 |
| 9 | Human-in-the-Loop | 指在 AI 或 Agent 的决策与执行流程中引入人工参与，通过人工审核、确认或干预来提升准确性、安全性与可控性。 | 在自动回复客户邮件前，系统先生成草稿并由人工一键确认后再发送，这就是典型的 Human-in-the-Loop 流程。 |
| 10 | Harness | 指承载和托管 Agent 系统运行的上层框架，负责把 Runtime、Controller、Planner、Memory、工具连接与治理机制组织成可持续运行的整体。 | 在企业级多智能体系统中，Harness 负责统一管理任务生命周期、权限边界、监控告警与发布策略，让多个 Agent 能稳定协作。 |
| 11 | MCP（Model Context Protocol） | 一种让模型以统一协议连接外部工具、数据源与上下文资源的标准接口，帮助 Agent 在多工具场景下实现可扩展、可治理的集成能力。 | 团队把 GitHub、Postgres、飞书等能力封装成 MCP Server 后，Agent 可以通过统一方式发现并调用这些工具，而不需要分别适配每个系统。 |
| 12 | 流式输出（Streaming） | 指模型一边生成、一边把结果分成小块推送给调用方，而不是等整段生成完再一次性返回。相对「非流式」，它大幅缩短「看到第一个字」的等待时间，代价是调用方要把每一块增量自己拼起来。 | 聊天界面里回答逐字浮现就是流式；同一句话实测首个字延迟从非流式的 1.75 秒降到 0.53 秒。代码里对应 `stream: true`，响应是一串 `delta` 增量块（非流式则是 `message` 里一次给全）。 |
| 13 | 关键词检索（Keyword Search） | 指拿查询里的字面词去匹配内容，命中相同的词才算找到。实现简单，查明确字段时精准；缺点是语义理解能力弱——说法一变就搜不到。 | 用户说「pnpm 怎么配」，而记忆里存的是「包管理器偏好」——两边没有一个字相同，关键词检索一条也召不回。 |
| 14 | 向量检索（Vector Search） | 指把查询和内容都转成向量，按语义相似度来找，因此说法不同也能对上。代价是每段内容都要先过一遍 embedding 服务，而它通常得另接一家厂商。 | 同一句「pnpm 怎么配」，向量检索能召回「包管理器偏好」那条——两句讲的是同一件事，靠的是语义而不是共同的字。 |
| 15 | stdin（标准输入） | 进程启动时拿到的输入通道，操作系统给它的编号是 0。程序从它读数据——`for line in sys.stdin` 就是逐行读它。 | MCP 服务端从 stdin 逐行收客户端发来的 JSON-RPC 消息；客户端关掉 stdin，就等于通知它「该退出了」。 |
| 16 | stdout（标准输出） | 进程输出正常结果的通道，操作系统给它的编号是 1。它只该放程序要产出的内容——混进别的东西，读它的那一方就会出错。 | MCP 服务端把每条应答写进 stdout。stdio 传输把这条通道当作协议专用，混进一行 `print` 日志，客户端就在那里解析失败。 |
| 17 | stderr（标准错误） | 进程输出错误与诊断信息的通道，操作系统给它的编号是 2。它和 stdout 是两条独立通道，所以日志写这里不会污染正常结果。 | MCP 服务端的启动日志和执行失败记录全走 stderr——这正是它能让 stdout 保持干净、只跑协议消息的原因。 |
| 18 | 进程（Process） | 一个正在运行的程序实例，有自己的内存空间和编号（PID），由操作系统创建和调度。要点是内存隔离——两个进程互相看不见对方的变量，要交换数据只能走操作系统提供的通道（如管道）。 | MCP 服务端就是被 Agent 用 `subprocess.Popen` 起出来的另一个进程：Agent 不能直接调它里面的函数，只能把参数转成 JSON、写进管道传过去。 |
| 19 | 内存（RAM） | 程序运行时临时放数据的地方，由操作系统分配给进程。读写快，但进程一结束（正常退出或崩溃都一样）就被系统收回，里面的数据一起消失。想在进程死掉后留住数据，必须主动写到磁盘上。 | 文中那份 `msgs` 对话历史只在内存里——Agent 跑到一半崩了，前面几步查过的数据和花掉的 token 全丢，只能从第一步重来。 |
| 20 | 磁盘（Disk） | 长期保存数据的地方，断电或程序退出都还在。读写比内存慢几万倍，所以程序不会每改一点就写一次盘，而是定期存一次。 | 演示用的 `ad.db` 在磁盘上——进程崩多少次，投放数据都还在，所以工具每次都查得到；而 Agent 的进度每次归零。 |
| 21 | CMD 与 PowerShell | Windows 上的两代命令行：CMD 源自 DOS，管道里传的是文本；PowerShell 传的是对象，因此能直接按属性筛选排序，而 CMD 只能做字符串匹配。另外 PowerShell 是完整的编程语言，CMD 的 .bat 基本只能顺序执行命令。 | 找占内存超 100MB 的进程——CMD 只能 `tasklist \| findstr chrome` 做文本匹配，比不了数值；PowerShell 里 `Get-Process \| Where-Object {$_.WorkingSet -gt 100MB}` 一行就出来了。 |
| 22 | 幂等（Idempotent） | 指同一个操作执行一次和执行多次，结果完全一样——重复执行不会产生额外效果。相对的「不幂等」则指每执行一次就多一次副作用。判断依据是**结果**而非过程：执行了两次、但最终状态与执行一次相同，仍算幂等。 | 重试是典型场景：查询类操作天然幂等，请求超时后重发没有风险；而下单、扣款、发消息不幂等——超时重试就可能下两单、扣两次钱。所以不幂等的操作要配去重键（如订单号），让重复请求被识别并丢弃。 |
