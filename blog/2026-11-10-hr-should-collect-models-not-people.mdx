> 我最近在做一件事：**把我用过的、好用的第三方 API key 全部归档一遍**。
> 整理到一半，我突然愣住了——**这不就是人力老大干了几十年的活儿吗？**

<!-- truncate -->

## 一个建人才库，一个建模型库

人力老大日常在干三件事：

- 去哪儿找到好的人
- 判断这个人适合什么岗位
- 怎么留住他，让他在关键时刻顶得上

我整理 key 的时候，干的是**一模一样**的事：

| 人力老大 | 我 |
|---|---|
| 人才库 | 模型 / key 库 |
| 招聘渠道 | 官方 API、第三方中转 |
| 薪资预算 | token 额度 |
| 「这人适合做技术」 | 「这模型擅长写代码」 |
| 「这人便宜又能扛」 | 「这个量大便宜，适合跑批」 |
| 「关键项目上最贵那个」 | 「难活儿交给强模型」 |

**连「面试」这一步都有**——我拿同一个问题去试不同模型，看谁答得准、谁更快、谁更便宜。这不就是结构化面试吗。

## 模型就是员工，脾气还都不一样

手里常用的几个，各自的定位很清楚：

- **有的擅长长文本** —— 几十页文档喂进去，它不迷糊
- **有的写代码利索** —— 改 bug、写脚本，开箱就用
- **有的便宜量大** —— 跑批、做粗活，性价比之王
- **有的贵但关键时刻靠得住** —— 复杂推理、要出真结果的时候，只能它上

**跟带团队一模一样。** 你不能让所有人干一样的活，也不能因为最贵那个强，就把其他人都裁了。

**用错模型，就是用错人。**

同一个任务，A 模型 30 秒出活，B 模型绕半小时还没绕明白——你损失的不是钱，是判断力。

## 为什么必须整理

两个理由：

**第一，不整理你永远在重复踩坑。**

哪个模型在什么场景翻过车，你不记下来，下次还会踩。这跟「这人上次这个项目掉链子，我忘了」是一回事。

**第二，这行的迭代速度，比招人快得多。**

你今天收集的这一套，过几个月可能就有一半要更新。**不维护的 key 库，等于一份三年前的简历池**——看着挺厚，真用起来全是过期的。

## 我打算怎么整理

不搞复杂的，一张表就够。每条 key / 模型记七个字段：

| 字段 | 记什么 |
|---|---|
| 模型名 | 具体版本，别只写「GPT」 |
| 渠道 | 官方还是第三方中转 |
| **擅长什么** | 一句话，这是最有价值的一栏 |
| 价格 | 输入/输出分别多少 |
| **实测感受** | 我自己用下来的体感 |
| **什么场景用它** | 决策依据——下次不用重新想 |
| 状态 | 还能不能跑、额度还剩多少 |

**中间三栏是核心。** 光记「我有哪些 key」没用，要记「这个 key 什么时候该派它上场」。

## 所以我说，人力老大真该改行了

不是人的价值没了。

是说——**「识别什么能力适合什么任务」**这件事，正在从人身上，转移到模型和工具身上。

**以前是「我招谁进来」，现在是「我调谁来干」。**

本质上你还是在做同一件事：**判断、组合、调度**。

只不过「团队成员」的名单，从一张通讯录，变成了一列 key。

**人力老大该做的，是把这套本事用在新对象上——去找模型，去找 Agent。**

因为现在最稀缺的，已经不是「找不到人」，

是**「手里有一堆模型，却不知道该派谁上」**。
